Build a full-stack web application called "Review Radar — 
Customer Decision Engine".

Core idea: Turn messy Amazon reviews into clear, actionable 
product and marketing decisions for e-commerce sellers.

---

## USER FLOW

1. User pastes an Amazon product URL
2. App scrapes that listing + automatically finds 
   and scrapes 9 competitor listings in the same category
3. Collects 500–1000 reviews across all listings
4. Runs a multi-role AI pipeline using Groq
5. Displays a Decision Dashboard with insights, gaps, 
   and ready-to-use listing copy

---

## SCRAPING LOGIC

### Step 1 — Scrape Main Listing
From the Amazon URL the user provides, extract:
- Product title
- Brand name
- Price
- Star rating
- Total review count
- Best Seller Rank (BSR) — parse from product details section
- ASIN — extract from URL pattern /dp/XXXXXXXXXX/
- Bullet points (the 5 feature bullets)

### Step 2 — Find 9 Competitors
Using the product title keywords, construct an Amazon 
search URL and scrape the first 9 ASINs that are not 
the user's own product. Then scrape each competitor's 
listing for the same fields above.

### Step 3 — Scrape Reviews
For each listing (main + 9 competitors):
- Scrape up to 5 pages of reviews
- From each review extract: star rating, title, body text
- Target: 50–100 reviews per listing

### Step 4 — Headers to avoid blocks
Use these headers on every scraping request:
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) 
AppleWebKit/537.36 (KHTML, like Gecko) 
Chrome/120.0.0.0 Safari/537.36
Accept-Language: en-US,en;q=0.9

Add a 1–2 second random delay between each request.

### Step 5 — ScraperAPI fallback
If any request returns a CAPTCHA or bot-detection page 
(check if response body contains "robot" or "captcha"),
retry through ScraperAPI:
http://api.scraperapi.com?api_key={SCRAPERAPI_KEY}&url={encodedUrl}

Base URL: https://api.groq.com/openai/v1/chat/completions

Run these 5 AI roles sequentially. Each is a separate

Add 500ms delay between each call to respect rate limits.
All responses must be returned as JSON only — 
strip any markdown code fences before parsing.
Wrap all JSON parsing in try/catch with fallback empty arrays.

## REVENUE ESTIMATION (no AI needed — pure math)

Use this BSR-to-monthly-revenue formula:

BSR 1-100 → 150 units/day
BSR 101-500 → 80 units/day  
BSR 501-1000 → 50 units/day
BSR 1001-5000 → 25 units/day
BSR 5001-10000 → 12 units/day
BSR 10001-50000 → 5 units/day
BSR 50001-100000 → 2 units/day
BSR 100000+ → 0.5 units/day

Monthly revenue = dailyUnits × 30 × price

Calculate this for all 10 listings.
Total market size = sum of all 10 monthly revenues.

## IMPORTANT TECHNICAL NOTES

1. ASYNC PROCESSING IS CRITICAL
   The /api/analyze endpoint must respond in under 2 seconds.
   All scraping and AI calls run in the background.
   Frontend polls /api/status every 3 seconds until COMPLETE.

2. UPDATE PROGRESS IN REAL TIME
   As each step completes, update progress_message and 
   percent_complete in the database immediately.
   This makes the processing screen feel alive and trustworthy.

3. GROQ RATE LIMITS
   Add 500ms sleep between each Groq API call.
   Never call Groq more than 2 times per second.

4. REVIEW TRUNCATION
   Never send more than 6000 characters to Groq in one call.
   If reviews exceed this, take the most recent ones 
   first until you hit the limit.

5. FAILED SCRAPES
   If a competitor listing fails to scrape after 2 attempts, 
   skip it and continue. Never crash the whole report 
   for one bad URL.

6. JSON PARSING SAFETY
   Always strip markdown fences (```json) before parsing 
   Groq responses. Wrap every parse in try/catch. 
   If parsing fails, store empty array as fallback 
   and continue to next role.

7. SHARE TOKEN
   Generate the share token immediately when report 
   is created (status=PENDING) so the URL works 
   even during processing.

8. RATE LIMITING
   Max 3 analyses per IP per hour to protect API costs.

9. NO MOCK DATA
   Every number, insight, and recommendation must come 
   from real scraped data or real Groq analysis. 
   No placeholders. No hardcoded examples.

10. SCRAPERAPI FALLBACK
    Only use ScraperAPI when direct scraping is blocked. 
    It is the fallback, not the primary method.
